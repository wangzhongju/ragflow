3.4 官方资源缓存与可选 SSH 隧道

资源清单固定官方 URL、版本/提交、大小和 SHA-256。模型来自 InfiniFlow 的 Hugging Face 仓库，NLTK 来自 nltk/nltk_data，Tika 来自 Apache，tiktoken 来自 OpenAI 公共资源。资源下载到 third_partys；有效文件跳过，损坏文件重下，未完成下载不替换原文件。NLTK 的解压文件也逐项校验，缺失时从本地 ZIP 恢复。

bash docker/docker.sh fetch         # 下载缺失资源并校验
bash docker/docker.sh fetch --check # 只校验，完全不联网

third_partys 被 Git 忽略，可复制到其他机器后执行 fetch --check；新机器也可直接 fetch 重建。apt、Python/npm 包使用 BuildKit 缓存，首次安装仍需网络；资源齐全不代表可以完全断网重建镜像。

本地已有 HTTP 代理（示例端口 7897）时，在本地 Windows 终端保持以下 SSH 连接。隧道只绑定 91 回环地址：

5. 模型目录与配置

通义模型同步范围与规则

入口为 sync_model_catalog.py，在 91 Linux 宿主机运行；Python 3.10 标准库负责操作文件/容器，数据库和 HTTP 依赖使用现有应用容器。在隔离环境先执行 plan。91 与 92 共用数据库，apply/rollback 会修改共享模型数据，只用于批准的生产维护。

官方 查询模型列表 API 提供分页总数、模态、能力、上下文及下线信息。北京业务空间的新域名为 https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/models；本部署已有的 https://dashscope.aliyuncs.com/api/v1/models 本次实测可用。工具只向后者发送当前北京实例密钥，并固定 service_site=asia-pacific-china、supports=inference，不筛除平台上的第三方推理供应商。其他地域或业务空间域名需要先审阅并扩展地域策略，不能直接把密钥转发到任意 URL。

这里同步的是官网目录元数据，不是逐模型推理验收。全量官网条目进入快照；RAGFlow 目录只增加当前适配器具有对应调用路径的模型。账号余额、权限、额度和生成质量仍需独立验收，新项的 verify=unknown，不会伪造验证成功。

情况 处理
新增模型 分页取完全部官方条目，根据能力和现有适配器生成目录项，并注册到指定实例
规格/能力变化 更新上下文预算、模型类型、工具调用和思考标记；已有模型 ID、状态、验证结果及其他自定义 extra 保持
明确下线且已到生效时间 按官方 offline_time 或策略中的公告清单删除；列出涉及的流程引用，不自动替换流程模型
未来下线 暂保留，在报告中给出生效时间；维护策略中的公告记录，避免后续来源列表移除条目后丢失下线证据
旧项在列表缺席 保留并报告，不把接口缺席、地域差异或别名差异当作已下线
无对应适配器或关键规格缺失 新项不注册，写入 excluded；旧项原样保留并写入 retained_for_review
请求失败、分页缺失/重复、总数变化、未知下线结构 中止生成计划，不使用残缺数据更新目录

TR 同时包含文本 Embedding 和 Rerank，不能全部映射成 embedding。当前仅支持已核对调用协议的文本向量/排序、普通 Chat/Vision、Qwen3-ASR/Fun-ASR-Flash 以及 Sambert TTS。图像/视频生成、实时会话、部分 Omni、异步向量及新音频协议等完整保存在官网快照中，待适配器支持后再扩展 _normalize，不能仅增加名称就声称可用。

max_tokens 对 Chat 表示上下文预算，不是最大输出 Token；例如 qwen3.8-flash 官方返回上下文 1,000,000、最大输出 131,072。原始全部规格保留在 official.json。官方未提供数值的条目使用有来源的补充策略，音频时长/字符限额不会伪造成 Token 上下文。现有 Embedding 适配器还会截断输入，目录规格更新本身不会改变解析或截断算法。

维护策略与上线前准备

tongyi-sync-policy.json 维护以下内容：

  • 同步服务商和地域；当前为 Tongyi-Qianwen / 中国部署范围。
  • 官方下线公告的来源、准确模型 Code 和生效日期。下线清单的首次核查见历史记录；后续核对模型下线公告，只补入公告明确列出的名称。
  • 官方列表缺少 Token 数值时的补充值和来源，例如 text-embedding 系列参照同步向量 API。接口有明确正数时优先使用接口值；文档出现不同口径时先区分单条、单批次、上下文和输出限制。

应用、重新加载与验收

python3 docker/scripts/sync_model_catalog.py verify --work-dir "$run"

11. 外部 Agent 文件解析接口

适用于 Python API。接口复用现有解析器，返回文本，不写入知识库或对象存储。外部 Agent 可使用 文件解析 Skill。

接口契约

两个接口均使用已有用户 API Key：Authorization: Bearer <API Key>，不是登录密码或 Beta token。

  • GET /api/v1/files/parse：返回 data.extensions、max_file_bytes、layout_modes、format。
  • POST /api/v1/files/parse：multipart/form-data，恰好一个 file；可选 layout_recognize，值为 Plain Text（默认）或 DeepDOC。其他字段、多个文件、空文件、未知扩展名拒绝。

单文件最大 20 MiB；multipart 整体最大 20 MiB + 64 KiB，部署的全局请求或代理限制更小时以更小值为准。支持 pdf/doc/docx/txt/md/markdown/html/htm/csv/xls/xlsx/json/jsonl/epub；扩展名支持不等于任意内容均可解析。Office、PDF、OCR 仍依赖服务端现有解析组件。普通文本模式不保证读取扫描 PDF，扫描件需 DeepDOC。响应为文本，不承诺版面坐标、图片或无损还原。

成功示例：

{"code":0,"data":{"filename":"example.txt","size":5,"format":"text","content":"\n -----------------\nFile: example.txt\nContent as following: \nhello","layout_recognize":"Plain Text"}}

文本保留现有解析器生成的文件标题、分块拼接和表格标记。客户端应同时检查 HTTP 状态和 code；文本/HTML 为不可信文档内容，不能直接作为指令或未经清洗插入页面。

错误：400 输入错误；413 文件/请求过大；415 请求格式错误；422 解析失败（详细异常仅在服务日志）。认证失败沿用系统现有认证返回约定。同步调用通过现有有界长任务线程池执行；没有作业查询/取消接口，客户端超时不意味着底层解析终止，也没有结果持久化或自动重试。适合小文件即时解析，批量长任务仍应使用知识库异步入库流程。

单块接口的确切行为

PATCH /api/v1/datasets/{kb}/documents/{doc}/chunks/{chunk} 在 chunk_api.py 中：

  1. 校验库、文档、chunk 归属；保持 chunk ID。
  2. 从提交正文生成 content_ltks/content_sm_ltks。
  3. 用该文档所属库的 Embedding 模型重新编码。t4 非 QA，当前请求是 0.1 × 文件名向量 + 0.9 × 正文向量，与 t4 Tokenizer 的权重一致。
  4. 更新 ES 同一记录的正文、分词和 q_1024_vec；ES 在 refresh 后将新分词用于检索，无需全库重建。

注意：接口不会重新生成摘要、问题、关键词、Graph；现有问题/关键词只有显式提交时才更新。若提交 questions，其非空内容可作为编码输入。通用接口也不重放其他流程自定义的字段/权重策略；此处结论已对照 t4 的 fields=[text]、文件名权重 0.1。普通 GET chunk 会隐藏向量和分词字段，严格验收要读取 ES。当前 PATCH 没有检查底层 update 返回的布尔值，不能只看 HTTP 200/业务码 0 就断言写入成功，必须回读。

“从当前步骤重新运行”的实际范围

rerun_agent 会先删除当前文档的 ES 记录及旧任务，重置其统计，再以请求 DSL 排队；Pipeline.run 复用选中节点输出，从它的下游执行。因此这不是单个数组项的增量重跑，也不是后台自动监听字段变化。重跑过程中当前文档会暂时无法完整检索，失败也不会自动回滚。

文档级 Compiler 重新执行后，知识库级合并图谱仍是独立任务。只重新生成 Artifacts Graph 不能替代源 chunk 的重编码，也不能保证修复尚未重新编译的文档实体。

查看诊断报告中的 workers、queues、pipeline_log_ttl：

  • lag 表示尚未投递给消费者的条目；pending 是已投递但尚未 ACK 的条目，正常长任务也会 pending。
  • 心跳新、目标任务在 current_task_ids、底层日志增加：优先判断执行缓慢。

2. 为什么页面删除后仍有数据

现场容器中的知识库删除、文档删除、ES 索引删除三个实现文件，与本地对应文件的 SHA-256 一致，可以用本地代码解释当前行为：

  • api/apps/services/dataset_api_service.py::_delete_datasets_sync 主要删除知识库、文档、文件关联等，并调用各存储清理逻辑；这些操作不是跨 MySQL/ES/MinIO/Redis 的统一事务。
  • api/db/services/document_service.py::remove_document 按文档清理任务、分块和部分图片，但部分清理失败只记录日志。该路径没有完整清空 KB 对象桶及共享 imagetemps。
  • common/doc_store/es_conn_base.py::delete_idx 在传入 KB ID 时直接返回，因为同租户的多个 KB 共用一个 ES 索引。知识库级图谱和删除标记不能仅靠文档 ID 删除来全部覆盖。
  • rag/utils/base64_image.py::image2id 默认桶为 imagetemps；解析流程存在使用该默认桶的调用。它是共享存储位置，不能仅凭名称认定所有对象都可以删。

因此，要同时处理关系数据、检索数据、对象和任务状态。空桶、空索引、基础目录存在本身不影响从头构建。
