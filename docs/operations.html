2. 工程整体挂载与二次开发

宿主机完整工程以 bind mount 挂载到 /ragflow。API、Worker、解析代码、配置与工具直接读取 checkout；容器内源码编辑同步到宿主机。运行环境 Dockerfile 不 COPY 应用源码，已有进度及 Graph 修复直接来自挂载源码。

容器路径来源
/ragflow宿主机工程根目录，可读写。
/ragflow/.venv按镜像 ID 区分的只读 Python 依赖卷，首次由 Docker 从镜像填充。
/ragflow/rag/res/deepdoc对应镜像的只读 OCR 模型卷。
/ragflow/web/dist、/ragflow/bin对应镜像的前端和二进制只读卷；APP_WEB_DIST 可改用宿主机前端产物。
/ragflow/conf/service_conf.yaml绑定 docker/state/service_conf.yaml，生成配置不覆盖工程原文件。
/ragflow/logs、/opt/ragflow-ops日志持久化目录、只读运维脚本目录。

整目录挂载会遮住镜像原 /ragflow，因此运行依赖需单独挂载。Tika JAR、tokenizer 缓存和版本文件由镜像 /opt/ragflow-runtime 补齐到忽略管理的运行文件，不包含应用源码。镜像 ID 改变会自动创建新依赖卷；旧卷保留供回退，不能盲目清理。

# 修改 Python 源码后重新加载
bash docker/docker.sh restart app
# 前端修改需编译
cd web
npm ci
npm run build
cd ..
# app.env 设置 APP_WEB_DIST=/home/cdky/workspace/github/ragflow/web/dist
bash docker/docker.sh recreate app

Python 依赖和原生库变化使用完整 Dockerfile 构建镜像，再更新 RAGFLOW_IMAGE 并重建应用。不要在只读依赖卷中安装包。未配置 APP_WEB_DIST 时使用镜像配套的预编译前端，源码修改本身不会自动编译前端。

3. 初始化、构建与部署

3.1 新环境配置

cd /home/cdky/workspace/github/ragflow
bash docker/docker.sh init --app-ip 192.168.88.91 --storage-ip 192.168.88.92 --app-memory 48g
# 单机：两个 IP 都填主机地址，92 可设置 --app-memory 6g
chmod 600 docker/env/*.env

仅首次执行初始化；任何 env 已存在都会拒绝覆盖。分离部署将匹配的 app.env 和 storage.env 安全分发到对应主机；当前已有配置不能重新生成密码。应用配置不包含 MySQL root 密码。

APP_IP 控制应用绑定地址，APP_WEB_PORT / APP_API_PORT / APP_ADMIN_PORT 默认为 8088 / 9380 / 9381。MYSQL_HOST、REDIS_HOST、MINIO_HOST、ES_HOST 使用容器可达的存储 IP；同机仍使用 LAN IP，不能填容器自己的 127.0.0.1。STORAGE_IP 控制存储监听。

5. 模型目录与排障

任务及定点 Graph 恢复见 排障手册。恢复工具默认只读，--apply 才写日志并 ACK；本轮部署验证不执行恢复或计费模型调用。

模型同步是协调主机文件和应用重载的宿主机工具，从工程根目录运行。共享存储时选一个维护主机执行，然后同步另一端 conf/llm_factories.json 并重启另一端应用，避免两端内存目录不一致。

run="docker/backups/tongyi-sync-$(date +%Y%m%d-%H%M%S)"
python3 docker/scripts/sync_model_catalog.py plan --instance-id 实际实例ID --work-dir "$run"
# 审阅计划后应用
python3 docker/scripts/sync_model_catalog.py apply --work-dir "$run"
python3 docker/scripts/sync_model_catalog.py verify --work-dir "$run"
# 回退该次同步：python3 docker/scripts/sync_model_catalog.py rollback --work-dir "$run"

本地 Qwen3 Embedding 配置（2026-10-23 核验记录）

该模型服务位于 192.168.88.169:9502，不属于本次 91/92 存储部署，本轮未调用。此前核验模型为 qwen3-text-embedding，最大输入 2048 Token，输出 1024 维。

  1. 在“设置 → 模型提供商”添加 VLLM 实例，名称可用 local-qwen3-embedding，Base URL 填 http://192.168.88.169:9502/v1。密钥只填服务分配的值，不加 Bearer 前缀。
  2. 选择 qwen3-text-embedding，类型为 Embedding，最大 Token 数填 2048；不要将向量维度 1024 当作 Token 限制。
  3. 验证模型后保存，按需设置全局默认及具体知识库。全局默认不会替换已有知识库的模型。

Base URL 不要加 /embeddings。服务须从应用容器可达。即使新旧模型都是 1024 维，向量空间也不相同；先用独立知识库验证，迁移时为整库原文、编译结果和 Graph 统一重建向量，不能直接改 embd_id 混用旧向量。

6. 备份与恢复

6.1 在线 MySQL 备份

bash docker/docker.sh into storage mysql
umask 077
MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysqldump -uroot --single-transaction \
  --routines --events --triggers --set-gtid-purged=OFF --databases rag_flow \
  > /tmp/rag_flow.sql
exit
# 宿主机取出备份，请使用唯一文件名避免覆盖
mkdir -p docker/backups
chmod 700 docker/backups
docker cp ragflow-storage-mysql-1:/tmp/rag_flow.sql docker/backups/rag_flow.sql
chmod 600 docker/backups/rag_flow.sql

在线 SQL 备份不覆盖 ES、MinIO 和 Redis，不能作为全系统一致性备份。

6.2 全存储冷备

# 等待当前任务结束，两端应用主机分别执行
bash docker/docker.sh stop app
# 92：列出全部应用 API 地址
APP_STOPPED=1 APP_URLS="http://192.168.88.91:9380 http://192.168.88.92:9380" \
  bash docker/scripts/backup.sh

脚本检查端点不响应、七个卷确属 ragflow-storage 后停止存储，只读归档 mysql_data、es_data、es_snapshots、minio_data、redis_data、kibana_data、redisinsight_data；校验 gzip 并生成 SHA256SUMS。结束后只恢复原先运行的存储容器，不自动启动应用。检查状态健康后再分别启动两端应用。

APP_STOPPED=1 是操作者确认。网络不可达不能证明远端 Worker 已停，应检查每台主机的容器实际状态。同一备份集合还须保存两端 app.env、storage.env、源码版本与差异和镜像记录，权限 600。

6.3 恢复顺序

  1. 在独立位置校验 SHA256SUMS 和压缩包，先恢复到独立测试卷，不能覆盖在用数据。
  2. 使用备份对应版本的存储镜像。冷备数据解包到各自空卷；在线 SQL 导入独立 MySQL 实例。物理数据库目录不能直接跨大版本复制。
  3. 数据、env 密钥和代码作为一组切换。只恢复 MySQL 会造成 ES 向量、MinIO 对象、Redis 任务不一致。
  4. 停止全部应用写入，验证恢复存储健康和业务对象关联后再切换连接配置，重建应用。
  5. 使用独立探针和真实只读查询验收。保留旧卷以便回退，不运行全局清理。
