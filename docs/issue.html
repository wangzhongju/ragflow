3. 数据库连接警告反复出现的原因

2026-11-02 已通过当前代码和隔离连接复现。api/apps/__init__.py 的请求 teardown 调用 close_connection；api/db/db_models.py 对 MySQL 执行 DB.close_stale(age=30)。Peewee 的 close_stale 遍历整个池的已借出连接，按 checked_out 时间强制关闭底层连接；它不会同步重置其他线程持有的 Peewee 状态。因此同一连接可能出现 is_closed=False，而 PyMySQL open=False、_sock=None。下次 SQL 在客户端抛出 InterfaceError(0, '')，此时 SQL 尚未发给 MySQL。

RetryingPooledMySQLDatabase.execute_sql 捕获异常，输出 attempt 1/5，重连并 sleep(1) 后成功。137 是 API 进程 PID，(0, '') 是异常参数，并非 MySQL 服务端错误编号。多数请求首次重试就恢复，下一条使用被关闭连接的请求又从 attempt 1/5 开始。

同类问题的处理顺序

  1. 应用仍运行但 env/state 缺失时，不执行 init 或重建容器。先把在用容器的配置及原私有备份保存到受限目录，不能在共享终端输出完整环境变量。

  3. 恢复文件到 docker/env，目录权限 700、env 权限 600；在宿主工程根执行 bash docker/docker.sh config app（存储主机也检查 config storage），只验证配置不打印密钥。state 为派生文件，确认原私有配置齐全后再由正常入口生成。
  4. 进入应用检查 id、解释器、sudo 与个人配置；若 apt 报 Unable to locate package，先 sudo apt-get update 再安装，长期依赖写入镜像构建。重建后只保留在绑定 home 中的个人配置。
