按日期记录问题、处理方式与验证结果；详细步骤放入对应手册，不记录明文凭据。

## 2026-10-24

### 1. local 知识库报错及空 Graph 排查

#### 根因

- 本地 Embedding 正常：`local` 的用户手册已写入 31 个切片；从 91 容器再次请求返回 HTTP 200、1024 维。三次 `Arrearage` 来自图片理解，租户默认视觉模型仍是通义 `qwen3.8-max`。
- 两库实际执行路径不同：`db_t1` 文档绑定 `pipeline_t1`，`local` 现有文档的 `pipeline_id=NULL`，走普通解析，没有 Compiler 产物。仅修改知识库默认流程不会更新已有文档。
- `local` 两次 Graph 任务均以 `No doc_graph rows found.` 结束；ES 只有 31 个原文切片和 2 个删除标记，实体、关系及 Graph 均为 0。100% 表示任务结束，不代表生成了图。

#### 排查与处理边界

- 对照 MySQL 配置/任务/操作日志、Redis 队列、ES 分类统计及 Worker 日志，确认 `pending=0/lag=0`，不是队列卡住。当前两库各只有一份用户手册；开发者手册仅保留历史失败日志，不能沿用昨日“两文件待完成”的状态。
- 当前共享流程的 Extractor、Compiler 已选择本地 Chat，但 Parser 的 PDF VLM 仍指定通义；已记录逐项切换及现有文档重新绑定流程的步骤。重新绑定会清除该文档现有切片，本轮只排查，不重建数据、不修改模型配置或重启服务。
- 详细证据、可复现命令与恢复验收见 [troubleshooting.md 第 9 节](troubleshooting.md#9-2026-10-24local-报错与空-graph)。

### 2. 现有 Python 补丁有效性审查

#### 对照与验证

- 基线为官方 `v0.27.2/a024bea0c`。5 个运行文件及 4 个测试文件在本地、91、92 一致；当前应用容器的 5 个补丁文件也一致（统一换行后 SHA-256）。现有进度、PDF 批内回调、Graph 类型/完成字段及收尾 ACK 修改均有实际作用，保留。
- Windows Python 3.14 与隔离补丁镜像 Python 3.13 各通过 33 项定向测试。官方基线对照为 21 失败/12 通过；其中 PDF 的 4 项失败属于新增回调契约，不代表旧坐标算法错误。只修正基线类型来源后仍有 3 项完成字段测试失败，验证完成字段补丁独立必要。

#### 剩余问题

- 完成时间的“先读任务引用、再按 KB ID 更新”仍有并发竞态，不能宣称完全防止旧任务覆盖新任务时间；现有测试只覆盖读取时已出现新任务的情况。建议后续使用包含任务 ID 条件的原子更新。
- Graph 空输入成功、部分异常仍报 100% 属于官方合并器语义；本轮现场是无编译输入，未观测到实际合并异常。完整逐文件结论、测试边界及后续改进见 [troubleshooting.md 第 10 节](troubleshooting.md#10-现有改动相对官方-v0272-的审查)。本轮未新增或回退业务补丁。

## 2026-10-23

### 1. 应用与存储分离部署

- **需求**：91 部署新应用，92 部署存储，使用官方镜像并提供维护入口，不影响 91 旧服务。
- **处理**：以 91 的 v0.27.2（`a024bea0cd93f39e6652a42bf84dd20c55bc560b`）部署独立项目；92 运行 MySQL、Redis、MinIO、Elasticsearch、Kibana、Redis Insight。镜像下载受限通过本地代理转发解决；MinIO 使用已核验的官方镜像摘要。
- **数据**：按要求删除 92 的四个 `ragflow-v0272_*` 历史卷；归属不明的 `docker_minio_data` 保留。91 旧服务未操作。
- **验证**：服务健康、登录、存储读写、文件上传下载、重启持久化、冷备份、MySQL 恢复及 ES 快照通过。分离部署可行，但网络故障、带宽和资源配额仍影响可靠性与性能。
- **文档**：[部署与运维手册](install.md)；镜像摘要见 `docker/split/images.lock.json`。尚未完成压力测试和完整灾备演练。

### 2. 工程一致性与 Name 历史候选

- **核对**：本地、91、92 的提交及 6,000 个工程项一致（本次修复后复核）；不含被忽略的运行配置、凭据和数据。Windows Git 显示的两个链接变更，经核验链接目标一致。
- **原因**：Compilation operator 的 Name 未关闭浏览器自动补全，代码没有名称候选接口；当时数据库和部署包也无对应历史名称。证据支持浏览器表单记录，具体输入来源未追溯。
- **处理**：可用全新浏览器配置文件复核，或清理自动填充表单数据；未修改业务代码和用户数据。

### 3. PDF 处理停留在 17.33% 的排查

- **现象**：23 页用户手册已完成，146 页开发者手册长时间显示 17.33%。
- **原因**：开发者手册仍在 CPU DeepDOC 表格方向识别，8 核配额持续触发限流；50 页批次回调间隔超过 30 分钟，Redis 进度轨迹过期，重算比例降低又被单调更新规则忽略，因此百分比保持旧值。
- **处理**：新应用内存改为 48 GiB，取消 CPU 硬配额；进度改为独立保存节点状态，增加 PDF 批内回调，保留原解析参数。
- **Graph**：统一任务类型、修正完成时间字段，隔离日志异常与队列 ACK；已补回旧 Graph 成功日志并确认对应消息，未重算旧 Graph。
- **验证**：补丁已部署；本地/镜像内 33 项测试及真实 MySQL/Redis 进度验证通过。146 页文件完成 Compiler 后，最终 Embedding 因 `Arrearage` 被拒绝，文档仍失败；运行输出已保存。
- **后续**：本地 `qwen3-text-embedding` 接口测试成功（1024 维），页面配置写入部署手册第 10 节；原库旧模型不同，需要统一重建向量后再验收两文件 Graph。
- **文档**：[完整排查手册](troubleshooting.md)，[部署手册第 9 节](install.md#9-2026-10-23-资源与任务收尾补丁)；工具位于 `docker/split/`。
